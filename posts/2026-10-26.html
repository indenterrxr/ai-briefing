2026년 10월 26일 KST 기준. 오늘의 흐름은 AI를 “대화창에서 답하는 도구”에서 계속 일하는 대리인과 운영 가능한 플랫폼으로 바꾸는 과정에 있다. Anthropic은 앱을 연결해 백그라운드에서 업무를 수행하는 Claude Duet을 연구 프리뷰로 열었고, 개발자에게는 첫 API 버전 전환 경로를 제시했다. OpenAI는 모델 라우터·AI 게이트웨이에도 직접 서비스와 같은 수준의 안전장치를 요구하는 정책을 발표했다.

1. Claude Duet: 요청을 기다리지 않고, 연결된 업무를 살피는 에이전트

Anthropic은 10월 21일 Claude Duet 연구 프리뷰를 공개했다. Claude Duet은 사용자가 연결한 앱을 바탕으로 필요한 일을 알려 주고, 요청한 작업을 수행하며, 사용자가 자리를 비운 뒤에도 계속 작업하도록 설계된 별도 앱이다. 현재 미국의 Claude Pro·Max 구독자를 대상으로 대기자 명단을 통해 접근을 열고 있으며, iOS·Android와 Claude 웹에서 제공된다.

‘능동성’은 편의성과 권한 통제가 함께 필요하다

  • 업무 방식: 사용자는 텍스트나 음성으로 일을 지시하고, Duet은 연결된 앱의 맥락을 바탕으로 작업을 이어 간다.
  • 백그라운드 실행: 일반 채팅처럼 사용자가 매번 다음 메시지를 보내지 않아도 진행 상황을 살피고 필요한 때 알리도록 설계됐다.
  • 행동 전 확인: 메시지 전송, 결제, 문서 서명, 삭제처럼 되돌리기 어렵거나 영향이 큰 행동 전에는 사용자에게 확인을 묻는다고 Anthropic은 설명한다.
  • 프리뷰의 한계: 기능·접근 범위는 실험 기간에 바뀔 수 있고, Team·Enterprise 요금제에는 아직 제공되지 않는다.

이런 제품의 평가 기준은 단순한 답변 품질을 넘어선다. 에이전트가 무엇을 우선순위로 판단하는지, 어떤 데이터·도구에 접근하는지, 그리고 언제 승인을 멈추고 기다리는지가 실제 신뢰성을 결정한다. ‘알림을 줄이는 것’과 ‘중요한 일을 놓치지 않는 것’ 사이의 균형도 연구 프리뷰에서 검증해야 할 핵심이다.

2. Claude API, 2023년 이후 첫 정식 버전 전환

Claude Platform은 API 버전 2026-10-21과 마이그레이션 가이드를 공개했다. SDK를 쓰지 않는 경우 anthropic-version: 2026-10-21 헤더를 지정해야 하며, SDK 사용자는 새 버전을 쓰면 이 API 버전이 적용된다. Anthropic은 가능한 최신 버전 사용을 권하지만, 이전 버전 2023-06-01을 당장 중단한다고 발표한 것은 아니다.

업그레이드 전에 확인할 호환성 변경

  • 샘플링 설정: Messages·Message Batch 요청의 temperature, top_p, top_k는 새 버전에서 보내면 400 오류가 난다. 기본값 외 설정에 의존했다면 결과 재현성을 다시 검토해야 한다.
  • 메시지 구조: assistant 메시지에 직접 넣은 document 블록과 user 메시지 텍스트 블록의 비어 있지 않은 citations 배열은 오류 처리된다.
  • 관리 API 응답: RBAC, API 키, Enterprise Analytics 일부 필드명이 바뀌거나 제거된다. 대시보드·비용 리포트·권한 자동화 코드는 특히 영향 범위를 확인해야 한다.
  • 모델별 경로: Amazon Bedrock에서 이전 세대 모델을 호출한다면 새 버전 지원 여부와 모델 전환 조건이 별도로 있다.

이번 변경은 API가 성숙할수록 ‘같은 요청을 보냈는데도 예전처럼 동작한다’는 기대가 약해진다는 신호다. 버전 헤더를 명시하고, SDK 업그레이드와 프롬프트·샘플링 회귀 테스트를 한 배포 묶음으로 다루는 편이 안전하다.

3. OpenAI, 모델 라우터와 AI 게이트웨이에 사전 승인을 요구

OpenAI는 10월 21일 일관된 안전 기준에 관한 발표와 개정 사용 정책을 통해, 제3자가 OpenAI 모델에 직접 접근하게 하는 모델 접근 중개 플랫폼·AI 게이트웨이는 사전 검토와 승인을 받아야 한다고 명시했다. 이 변경은 2026년 11월 20일부터 효력이 발생한다. 앱 내부 기능을 위해 OpenAI 모델을 통합한 경우만으로 이 요건이 적용되는 것은 아니라고 정책은 구분한다.

무엇이 달라지나

  • 안전 기준의 확장: 직접 API뿐 아니라 호스팅 파트너·리셀러 경로에서도 안전장치와 위반 대응을 맞추겠다는 방향이다.
  • 라우터의 역할: 여러 모델을 한 API로 중개하는 서비스는 단순한 기술 레이어가 아니라 접근 통제와 집행을 함께 책임지는 사업자가 될 수 있다.
  • 개발·조달 영향: 게이트웨이를 운영하거나 판매하는 팀은 승인 여부, 사용자 식별·오용 대응 방식, 공급자별 정책을 아키텍처와 계약 단계에서 점검해야 한다.

정책은 경쟁을 제한하기보다는 여러 접속 경로에서 안전장치가 빠지는 일을 줄이는 목적이라고 OpenAI는 설명한다. 다만 실제 영향은 승인 과정의 기준과 처리 속도, 그리고 각 중개 서비스가 사용자 데이터·오용 신고를 어떻게 다루는지에 달려 있다. 멀티모델 전략을 쓰는 조직이라면 비용과 성능 비교표에 공급자 정책 준수와 운영 연속성도 넣어야 한다.

오늘의 관전 포인트: AI의 가치가 ‘한 번 잘 답하는 모델’에서 ‘외부 도구를 가지고 지속적으로 일하는 시스템’으로 이동할수록, 능동성은 권한 설계와 감사 가능성을 요구한다. 제품 기능, API 버전, 접근 중개 정책이 동시에 바뀌는 이유다.
