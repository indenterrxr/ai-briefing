2026년 10월 27일 KST 기준. 오늘의 공통 주제는 AI 시스템이 더 많은 개인 맥락과 외부 도구를 다루면서 생기는 접근 제어·프라이버시·구조적 복잡성이다. ChatGPT는 저장은 유지하되 화면과 검색에서 숨기는 ‘잠금 대화’를 순차 배포했고, Google DeepMind와 싱가포르 GovTech은 메시지를 클라우드로 보내지 않는 기기 내 사기 탐지 모델을 소개했다. Anthropic은 반대로 너무 복잡해진 멀티에이전트 설계를 한 개의 주 루프로 다시 접는 방법을 공개했다.

1. ChatGPT ‘잠금 대화’: 저장과 노출 방지를 분리하다

OpenAI는 10월 20일 ChatGPT 릴리스 노트에서 잠금 대화(Locked chats)를 소개했다. 선택한 대화를 계정 안에 남겨 두되 일반 대화 목록·고정 목록·검색에서 숨기고, 4자리 계정 PIN 또는 지원 기기의 인증을 통해서만 열 수 있게 하는 기능이다. Free·Go·Plus·Pro 사용자를 대상으로 웹·iOS·Android·신규 데스크톱 앱에 순차 배포 중이며, Enterprise·Edu도 지원 범위에 포함된다.

이 기능이 하는 일과 하지 않는 일

  • 화면·기기 공유 대비: 잠긴 대화는 일반 검색과 사이드바에서 사라지고 Projects > Locked chats에서 별도로 연다. 모바일에서는 지원될 경우 Face ID·Touch ID·기기 잠금 해제를 함께 쓸 수 있다.
  • 파일·메모리의 경계: 해당 대화에서 올리거나 만든 파일도 보호되지만, 다른 Space에서 가져온 파일은 기존 접근 규칙을 유지한다. 잠긴 대화 내부에서만 생성된 기억은 일반 대화로 자동 전달되지 않는다.
  • 보안의 한계: OpenAI는 이것이 종단 간 암호화나 별도 암호화 금고를 만드는 기능이 아니며, 보존 기간이나 ‘모두를 위한 모델 개선’ 설정도 바꾸지 않는다고 명시한다.
  • 복구 불가 선택: PIN을 잊어 재설정하면 잠긴 대화와 그 안에만 있던 기억·파일이 영구 삭제된다. 조직의 보존·컴플라이언스 규정도 이 기능으로 우회되지 않는다.

따라서 잠금 대화는 ‘민감한 내용을 서비스에서 없애는’ 임시 대화의 대체품이라기보다, 같은 기기에서 화면을 공유하거나 기록을 함께 보게 될 때를 위한 접근 분리 기능에 가깝다. 저장·학습·보존 설정이 어떤 상태인지와 공유 링크가 남아 있는지를 별도로 점검해야 한다.

2. Google DeepMind·싱가포르 GovTech: 대화 데이터를 올리지 않는 사기 탐지

Google DeepMind와 싱가포르 정부기술청(GovTech Singapore)은 기기 내 사기 탐지용 미세조정 모델 협업을 공개했다. 현지 사기 대화 예시로 경량 Gemma 모델을 미세조정해, 앱에 통합될 경우 대화 내용을 서버에서 스캔하지 않고 기기에서 조작적 대화 패턴을 분석하는 방식이다. 투자 사기, 가짜 구인, 공공기관·은행 사칭처럼 지역 맥락이 강한 사기를 겨냥한다.

배터리·오탐·프라이버시를 함께 다루는 2단계 설계

  • 1단계: 가벼운 분류기가 수신 메시지를 적은 전력으로 먼저 살핀다.
  • 2단계: 의심 신호가 있는 경우에만 미세조정 Gemma가 더 넓은 대화 맥락을 분석해 경고 여부를 판단한다.
  • 동의와 데이터 경계: 배포 시 사용자의 동의를 전제로 하며, 모델이 기기에서 실행되는 구조라 Google과 싱가포르 정부가 배포를 통해 사용자의 대화에 접근하지 않는다고 설명한다.
  • 학습 거버넌스: 미세조정은 GovTech 관리 GCP 환경에서 이뤄졌고, 사기 신고·정보 피드에서 파생한 익명 데이터셋을 사용해 시민의 개인 식별 정보는 학습에서 제외했다고 밝혔다.

이 발표는 완성된 대중 앱의 전면 출시가 아니라, 앱 안에서 단계적으로 도입할 모델·운영 방식을 제시한 것이다. 특히 사기 탐지에서는 놓치는 사례와 오탐 모두 비용이 크다. 실제 효과를 판단하려면 지역별 재현율·정밀도, 경고 뒤 사용자의 행동 변화, 앱별 동의 UX와 독립적 검증 결과가 뒤따라야 한다.

3. Anthropic의 역제안: 서브에이전트는 ‘측정해 보고’ 남겨라

Anthropic은 10월 22일 에이전트 설계 가이드와 Single agent loop kit을 공개했다. 요지는 라우터·플래너·도메인별 서브에이전트가 늘어난 시스템에서, 필요할 때만 스킬과 도구를 불러오는 하나의 주 에이전트 루프가 품질·비용·지연 시간에서 더 나은 경우가 있다는 것이다. 공개 가이드는 여러 기업 배포 사례에서 얻은 관찰이지 모든 업무에 적용되는 보편 벤치마크는 아니다.

‘한 개로 합치라’가 아니라, 평가로 결정하라는 제안

  • 왜 합치나: 에이전트 사이의 요약 전달에서 맥락이 손실되고, 팀마다 하나씩 만든 서브에이전트가 중복되며, 시스템 프롬프트가 충돌하는 ‘Frankenprompt’가 되기 쉽다.
  • 어떻게 합치나: 서브에이전트 프롬프트는 스킬로, API 호출은 MCP 도구로 옮기며 한 번에 하나씩 접는다. 전후의 작업 완수 평가를 비교해 남길 대상을 정한다.
  • 언제 유지하나: 단일 문맥이 커져 성능 저하가 측정되거나, 독립 과제를 새 문맥에서 병렬로 처리해야 하거나, 한 에이전트가 도구 선택·상충 지시를 잘 처리하지 못할 때는 서브에이전트가 적합하다.
  • 평가 우선: 가이드는 먼저 작은 종단 간 평가 세트를 만들고 반복 실행을 권한다. 키트 역시 참고 구현이며, 특정 구조가 항상 이긴다고 보장하지 않는다.

멀티에이전트는 역할 수만큼 성능이 좋아진다는 공식이 아니다. ‘누가 어느 문맥을 들고 있는가’, ‘정보를 요약하며 무엇을 잃는가’, ‘평가가 전체 작업을 실제로 측정하는가’가 더 중요하다. 조직의 책임 구분을 그대로 에이전트 구조로 복사하기 전에, 단일 루프와 비교 가능한 실험부터 만드는 편이 합리적이다.

오늘의 관전 포인트: AI가 대화·메시지·업무 흐름 속으로 더 깊이 들어갈수록 좋은 기능의 기준도 달라진다. 민감한 대화는 누가 볼 수 있는지, 사기 탐지는 어디에서 계산되는지, 에이전트는 왜 여러 개인지까지 사용자가 확인할 수 있어야 한다.
