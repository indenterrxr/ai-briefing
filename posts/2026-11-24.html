오늘의 한눈에 보기

오늘은 모델 이름 경쟁보다 AI가 실제 업무·파일·운영 환경으로 들어갈 때 생기는 비용과 통제가 핵심입니다. Google은 Gemini API가 큰 파일의 필요한 부분만 서버에서 읽게 하는 제어 기능을 내놨고, OpenAI와 Cisco는 패치가 배포되기 전의 Linux 시스템을 보호하기 위한 오픈소스 런타임을 공개했습니다. Anthropic의 기업 인터뷰는 AI의 가치를 비용 절감보다 산출량 확대로 보는 사례가 많지만, 병목과 조직 재설계가 관건이라고 짚습니다. Google Search는 Wallet·Drive·Gemini 맥락을 연결하는 개인화 기능을 opt-in 방식으로 확대합니다.

1. Gemini API, ‘파일 전체’ 대신 필요한 페이지만 읽는다

PDF·스프레드시트·영상·오디오의 범위와 표현 방식을 서버에서 선택

GOOGLE_FILE_SLICING Google은 11월 23일 Gemini API의 file slicing controls를 Google AI Studio와 Gemini 플랫폼에 출시했습니다. PDF·Office·OpenDocument·오디오·비디오를 업로드한 뒤, 모델이 확인할 페이지·시트 셀·시간 구간·콘텐츠 레이어와 해상도를 지정할 수 있습니다. 전체 파일을 먼저 텍스트나 프레임으로 풀어 보내는 대신, 필요한 범위만 서버 측에서 렌더링·토큰화하는 방식입니다.

  • 문서·슬라이드는 페이지 범위와 텍스트/이미지 레이어를, 스프레드시트는 시트·보이는 셀·수식·시각 요소를, 영상·오디오는 시간 구간을 선택할 수 있습니다.
  • 파일 URI는 여러 턴과 도구 호출에서 재사용할 수 있고, 에이전트가 함수 응답 안에서 다음에 볼 범위를 고르는 흐름도 지원합니다.
  • Google은 기존 파일 크기·페이지 제한은 유지된다고 밝혔으며, 지원 파트너의 자체 시험 사례를 소개했지만 모든 워크로드에서의 절감률이나 정확도를 보장한 것은 아닙니다.

실무적으로는 저비용 텍스트·미리보기로 위치를 찾고, 필요한 페이지만 고해상도로 재확인하는 2단계 패턴이 가능해집니다. 다만 잘못 고른 범위는 중요한 표·각주·프레임을 놓칠 수 있으므로, 선택 범위와 최종 근거를 로그로 남기고 전체 파일 처리와 정확도를 비교해야 합니다.

2. OpenAI·Cisco, 패치 전 시스템을 지키는 Shirudo 공개

AI 에이전트가 만든 eBPF 방어 규칙을 검증·서명한 뒤 실행한다는 설계

OPENAI_CISCO_SHIRUDO OpenAI와 Cisco는 11월 23일 Linux용 오픈소스 런타임 Shirudo를 발표했습니다. 영구 패치가 테스트·배포되는 동안에도 실행 중인 Linux 시스템을 재시작 없이 보호하는 것이 목표입니다. 발표에 따르면 AI 에이전트가 취약점을 발견하고 eBPF 기반 ‘shield’를 만들고 공격 차단·서비스 영향 여부를 시험하며, 검증된 shield만 가동되고 각 shield는 암호학적으로 서명됩니다.

  • eBPF는 운영체제 커널에서 작은 맞춤 프로그램을 실행하는 기술로, Shirudo는 이를 이용해 취약점 악용 패턴을 임시로 차단하려는 접근입니다.
  • Cisco는 Java4shell과 PHP 취약점에 대한 시험에서 탐지·차단 코드를 만들었다고 설명했습니다. 이는 통제된 시험 결과이지, 모든 취약점·운영 환경에서의 효과를 뜻하지는 않습니다.
  • 프로젝트는 GitHub에서 공개됐고 두 회사는 재현 테스트·커널 검증·정상 트래픽을 방해하는 사례의 기여를 요청하고 있습니다.
AI 보안의 다음 경쟁은 취약점 ‘발견’만이 아니라, 운영 중인 시스템에서 임시 완화책을 얼마나 검증 가능하고 되돌릴 수 있게 적용하느냐가 될 수 있습니다. 자동 생성 규칙에는 사람의 승인 경계와 오탐·서비스 영향 검증이 반드시 따라야 합니다.

3. Anthropic: 기업의 AI 가치는 ‘해고’보다 조직 재설계에서 갈린다

58개 기업 고객사 대상 66건 인터뷰가 보여준 도입의 병목

ANTHROPIC_WORKING_AI Anthropic 경제팀은 11월 23일 자사 엔터프라이즈 고객 58개사에서 진행한 66건의 인터뷰를 분석한 보고서를 냈습니다. 인터뷰 대상은 무작위 표본이 아니므로 전체 시장의 통계로 일반화할 수 없지만, 현장 도입 사례에서 많은 기업이 AI의 가치를 비용 절감보다 산출량 증가와 제품·서비스 개선으로 설명했다고 정리합니다.

  • 인터뷰에서는 AI 자동화가 직접 낳은 국내 해고 사례는 매우 적게 보고됐습니다. 반면 채용을 줄이거나, 특히 해외 외주·계약 업무를 축소했다는 사례는 나타났습니다.
  • 코딩 속도가 빨라질수록 코드 리뷰·영업·의사결정처럼 함께 빨라지지 않는 업무가 병목이 된다고 응답자들은 말했습니다.
  • 위에서 정한 자동화는 감시·저항·낡은 워크플로우라는 문제가, 개인별 실험은 편차·유지보수·공통 인프라 부족이라는 문제가 생겼습니다.

보고서의 결론은 ‘도입 좌석 수’보다 누가 결과를 검토하고, 어떤 역할이 끝까지 업무를 소유하며, 비개발자가 만든 내부 도구를 누가 유지할지를 설계해야 더 큰 가치에 도달한다는 것입니다. 따라서 이 결과는 Anthropic 고객의 정성적 관찰이라는 한계를 전제로, 조직·인력 전략을 점검하는 신호로 읽는 편이 적절합니다.

4. Google Search, Wallet·Drive·Gemini 맥락 연결을 opt-in으로 확대

개인화의 편의와 데이터 연결 권한을 같은 화면에서 관리해야

GOOGLE_PERSONAL_INTELLIGENCE Google은 AI Mode의 Personal Intelligence에 Google Wallet을 우선 연결하는 기능을 순차 출시하고, Drive와 Gemini 앱 연결도 향후 몇 주 안에 지원할 예정이라고 밝혔습니다. 사용자가 동의하면 지출·문서·대화 맥락을 Search 답변에 활용해 금융 목표 정리, 문서 기반 계획, 검색과 Gemini 사이의 맥락 이어받기 등을 돕는다는 설명입니다.

  • 연결은 Search Personalization의 Connected Apps에서 사용자가 선택하며, 언제든 연결을 끄거나 바꿀 수 있다고 Google은 설명합니다.
  • Wallet 연결에서 AI Mode는 계정 정보를 읽기만 하며, 돈을 이동·관리·투자할 수는 없다고 명시했습니다.
  • Google은 앞으로 응답 아래 Personalization 아이콘으로 어떤 맥락이 활용됐는지 보여주는 기능도 예고했습니다.

개인화는 ‘더 똑똑한 검색’이 아니라 여러 데이터 저장소를 잇는 권한 모델입니다. 업무·개인 계정을 분리하고, 연결 전에는 모델이 필요한 최소 데이터만 볼 수 있는지, 답변의 출처·컨텍스트 표시와 연결 해제 절차가 충분한지 확인하는 편이 안전합니다.

실무자가 바로 점검할 것

  • 대용량 파일: 전체 인입과 부분 인입을 같은 과제로 비교해 토큰, 지연 시간, 근거 누락률을 함께 측정합니다.
  • 자동 방어: 생성된 보안 규칙은 격리 환경에서 재현·회귀·성능 시험을 거치고, 승인·서명·긴급 해제 책임자를 분리합니다.
  • AI 도입: AI가 빨라진 앞단만 보지 말고 리뷰·의사결정·고객 대응·운영의 후속 병목과 유지보수 소유자를 함께 정합니다.
  • 개인화: 연결한 앱 목록을 정기적으로 검토하고, 지출·문서·대화 데이터가 섞여도 괜찮은 계정 경계를 먼저 결정합니다.

정리: 오늘의 발표들은 AI가 더 많은 일을 하게 만드는 동시에, 무엇을 읽을지·무엇을 실행할지·누가 검토할지·어떤 개인 데이터를 연결할지를 더 정교하게 결정하게 만듭니다. 비용 절감, 보안 자동화, 생산성, 개인화 모두에서 성패를 가르는 것은 모델 자체보다 그 권한과 검증을 설계하는 방식입니다.
